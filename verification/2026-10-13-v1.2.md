## vendored 闭包门禁探针（verification/vendor-probe.mjs，一次性探针）

目的：验证 vendored schemastery 可用，且产出的 Config 满足 dsh-settings / cordis-plugin-loader 的**真实门禁**——重点是 `dsh-settings` 的真实用法 `new z(schema.toJSON())`（用它自己的真库重建我们的 schema）。

命令：`node verification\vendor-probe.mjs`
原样输出：

```
~standard.vendor: schemastery
toJSON ok, has uid/refs: true true
rebuilt type: object dict keys: monitors
rebuilt monitors meta.volatile: true
validate({}) -> monitors.get(): {}
validate({monitors:{kimi:false}}) -> get(): {"kimi":false}
isVolatile(monitors) via cosmokit: true
VENDOR PROBE OK
```

覆盖六项：
1. `~standard.vendor === 'schemastery'` —— loader 的 `isSchemastery()` 鸭子类型检查通过。
2. `toJSON()` 存在且带 `uid`/`refs` —— `dsh-settings` 的 `schema(entry)` 门禁通过。
3. `new z(toJSON())` 成功重建 —— 官方库能反序列化我们的 schema。
4. 往返后 `monitors.meta.volatile === true` —— **关键**：volatile 标记未在序列化中丢失，否则 `volatileForm(schema)` 返回 undefined、entry 被丢弃。
5. 值语义正确：缺省 `{}`、显式 `false` 落值、`monitors` 是带 `.get()` 的 Volatile 引用。
6. `isVolatile()` 经 cosmokit 识别成功（跨副本经 `Symbol.for`）。

## 跨设备模拟（本次修复的核心证据）

**目的**：在旧代码必然降级的条件下验证修复成立。旧代码唯一可用的路径是「execPath 祖先目录探测应用自带副本」，因此把该路径彻底切断，即等价于「另一台布局不同的设备」。

**构造**：

1. 把 `plugin/` 复制到干净临时目录 `%TEMP%\tpd-foreign-device\`（无 `node_modules`、无任何 DSH 应用目录、无 `package.json` 依赖树）。
2. 把 `verification/smoke.mjs` 放到同级的 `verification/` 下（保持相对布局）。
3. 设 `DSH_APP_RESOURCES` 为**不存在的路径** `C:\nonexistent-dsh-resources`，确保应用自带副本兜底分支也必然落空。
4. 用 `node` 直接运行（该 `node` 经 `.desktop-bin\node.cmd` 解析，`execPath` 不在应用目录树内）。

## 对抗测试：vendored 闭包异常时的降级行为

**目的**：验证自带副本的存在不会把「降级」这条安全网变成「崩溃」。测试必须真隔离第 3 层（应用自带副本），否则在本机被它掩盖——第一次跑时正是如此：vendor 删掉后仍 `Config: present`，追查发现 execPath 祖先仍指向 DSH 安装目录。

**隔离方法**：把 `node.exe` **复制**到临时目录再运行（`execPath` 祖先树里没有 DSH），并设 `DSH_APP_RESOURCES` 为不存在路径。已用探针确认隔离生效：`ancestor hits = NONE`。

结果（原样输出）：

```
=== 基线：vendored 完好（真隔离），预期 present ===
Config: present

=== 攻击 A：vendor 缺失 ===
Config: degraded
inject: ["webServer","credentials"]
name: token-plan-dashboard
[token-plan-dashboard] @deepseek-ai/schemastery unavailable, monitor toggles disabled

=== 攻击 B：schemastery 语法损坏 ===
Config: degraded
[token-plan-dashboard] @deepseek-ai/schemastery unavailable, monitor toggles disabled

=== 攻击 C：cosmokit 损坏（schemastery 的传递依赖）===
Config: degraded
[token-plan-dashboard] @deepseek-ai/schemastery unavailable, monitor toggles disabled
```

**结论**：三种异常下插件均正常加载、`inject` 与 `name` 导出完好、仅 Config 降级并打印告警。即 vendored 闭包把「跨设备失效」修好了，同时保留了原有的降级安全网——**新增的依赖不会引入新的崩溃面**。

1. 自带 vendored 闭包在真实异机环境下确实被解析（第 1 顺位命中）；

3. 客户端 `configForms` 读到 `ready` 而非 `unavailable`，开关写入通道打通。
